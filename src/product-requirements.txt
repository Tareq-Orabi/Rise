# 1. الملخص التنفيذي — Executive Summary

## 1.1 تعريف المشروع

OctaClub + THINK مشروع تقني تابع لشركة OCTAGRAM يهدف إلى إعادة هندسة وتطوير النظام البرمجي الموجود سابقًا تحت اسم Medical Club، وتحويله إلى منصة تعليم جامعي شاملة ومستقلة وقابلة للتوسع، مع تطوير ودمج محرك ذكاء اصطناعي تعليمي باسم THINK.

لا تبدأ عملية تطوير OctaClub من نظام فارغ، ولا تعتمد على إعادة كتابة جميع المكونات البرمجية السابقة.

بدلًا من ذلك، يقوم المشروع على الاستفادة من المكونات الموجودة بعد فحصها وتوثيقها، وإعادة تصميم الأجزاء التي تحتاج إلى تعديل، وإزالة الوظائف المرتبطة بالنطاق القديم، وإضافة الوظائف الجديدة اللازمة لرؤية OctaClub.

بناءً على الخبرة السابقة في تطوير Medical Club، توجد قاعدة برمجية تشمل عددًا كبيرًا من الوظائف التي يحتاج إليها المنتج الجديد، خصوصًا في مجالات الحسابات والإدارة الأكاديمية والصلاحيات والمحتوى والخدمات الأساسية.

لكن وجود ميزة في المتطلبات السابقة لا يثبت أنها مكتملة في الكود الحالي. لذلك يجب التحقق من حالة كل مكون قبل اعتماده في خطة إعادة الاستخدام.

**الهدف الأساسي ليس إعادة بناء ما تم إنجازه، بل تحويل العمل السابق إلى منتج أفضل وأكثر تنظيمًا، مع توثيق كامل للبنية والوظائف والبيانات والتكاملات.**

## 1.2 استراتيجية المشروع

تعتمد الاستراتيجية على أربعة محاور:

### 1. System Recovery & Assessment

استرجاع وفحص النسخة البرمجية الحالية وتحديد حالة مكوناتها.

### 2. Software Re-engineering

إعادة هيكلة وتحسين وإعادة تخصيص المكونات الحالية لتناسب OctaClub.

### 3. Feature Expansion & THINK Integration

تطوير الوظائف الجديدة ودمج محرك THINK وبيئة التعلم التفاعلية.

### 4. Comprehensive Documentation

إعداد توثيق هندسي وتشغيلي ووظيفي شامل لجميع مكونات النظام.

## 1.3 النتيجة المطلوبة

بحلول 28 فبراير 2027، يتوفر إصدار Full Product V1 من OctaClub + THINK، يتضمن الوظائف الأساسية المتكاملة، ويعمل على بيئة إنتاجية مستقلة، مع توثيق يتيح فهم النظام وصيانته وتطويره.

لا يُعتبر المشروع منتهيًا إذا كانت الوظائف تعمل ولكن لا توجد مواصفات واضحة أو توثيق أو اختبارات مناسبة.

# 3. المبادئ الهندسية الحاكمة

**ENG-001 — Reuse First**

تتم مراجعة المكونات البرمجية الموجودة قبل اعتماد تطوير بديل.

**ENG-002 — No Unnecessary Rewriting**

يُمنع إعادة كتابة وظيفة مكتملة وآمنة وقابلة للصيانة لمجرد تغيير اسم المنتج أو تفضيل أسلوب برمجي مختلف.

**ENG-003 — Evidence-Based Refactoring**

يجب أن تستند إعادة الهيكلة إلى مشكلة فعلية أو متطلب جديد أو تحسين قابل للتبرير.

**ENG-004 — Full Documentation**

توثيق جميع الخدمات والوظائف والكيانات والتكاملات والقرارات المؤثرة إلزامي.

**ENG-005 — Preserve Verified Behavior**

عند إعادة هيكلة وظيفة، يجب الحفاظ على سلوكها الصحيح أو توثيق أي تغيير مقصود في ذلك السلوك.

**ENG-006 — Product Independence**

يجب أن يعمل OctaClub على مستودع وإعدادات وبيئات وبيانات وأسرار مستقلة، مع الاستفادة من كود MedClub المملوك لـOctagram.

**ENG-007 — Security by Design**

أي تعديل يجب ألا يؤدي إلى تراجع مستوى الحماية.

**ENG-008 — Modular Architecture**

تُحافظ المكونات على حدود واضحة تسمح بالتوسع والصيانة.

**ENG-009 — Traceability**

كل متطلب يجب ربطه بمكون برمجي أو API أو شاشة أو اختبار يثبت تنفيذه.

**ENG-010 — Documentation as Deliverable**

لا تعتبر الميزة منتهية قبل اكتمال توثيقها.

# 4. النظام الأساسي — Existing Medical Club System

## 4.1 نقطة الانطلاق

يُعتمد مشروع Medical Club السابق بوصفه المرجع التقني الأساسي لعملية إعادة الهندسة.

تُفحص الشيفرة وقواعد البيانات والمكونات والوثائق الموجودة لتحديد مدى صلاحيتها للاستخدام في OctaClub.

تشمل التقنيات التي سبق استخدامها في المشروع:

- ASP.NET Core / .NET.
- Entity Framework Core.
- PostgreSQL.
- REST APIs.
- Authentication & Authorization.
- Docker.
- Object Storage.
- Email Services.
- Background Processing.
- نظام إدارة أكاديمي.
- خدمات المحتوى والمستخدمين والإدارة.

يجب التحقق من الإصدارات والحالة الفعلية لهذه المكونات من المستودع والبيئة البرمجية، وليس اعتمادها بناءً على وصف سابق فقط.

## 4.2 التمييز بين المواصفات والتنفيذ

يجب فصل ثلاث حالات:

**Specified:** الميزة موجودة في وثائق المتطلبات القديمة.

**Implemented:** الميزة موجودة فعليًا في الكود.

**Verified:** الميزة تعمل وتم اختبارها وفق السلوك المطلوب.

لا تعني حالة Implemented بالضرورة أن الميزة صالحة للنقل أو النشر.

## 4.3 استقلال بيئات المنتج


لا تُنقل بيانات مستخدمي Medical Club، أو محتواه الخاص، أو أسراره، أو مفاتيح وصوله، أو معلوماته التشغيلية إلى OctaClub دون تصريح قانوني مناسب.

يكون للمنتج الجديد مستودعه وإعداداته وقاعدة بياناته وأسراره وبيئاته المستقلة.

# 6. تصنيف المكونات — Re-engineering Decision Matrix

كل مكون موجود يُصنف ضمن قرار واحد رئيسي:

| القرار | التعريف |
|---|---|
| RETAIN | الاحتفاظ بالمكون كما هو بعد اجتياز الفحص |
| REFACTOR | تحسين البنية مع الحفاظ على السلوك المطلوب |
| ADAPT | تعديل المكون ليتوافق مع متطلبات OctaClub |
| REWRITE | إعادة تنفيذ المكون عند وجود مبرر هندسي واضح |
| REMOVE | إزالة وظيفة لم تعد مطلوبة |
| NEW | تطوير وظيفة غير موجودة |
| BLOCKED | مكون لا يمكن اتخاذ قرار بشأنه قبل معالجة اعتماد أو مشكلة |

## 6.1 نموذج سجل القرار

لكل Module أو Endpoint:

**Component ID:** RE-COMP-001  
**Original Module:** Authentication  
**Current Status:** Pending Verification  
**Target Module:** OctaClub Identity  
**Decision:** Pending Audit  
**Reason:** يُحدد بعد الفحص  
**Required Changes:** تُوثق بالتفصيل  
**Owner:** يحدد  
**Dependencies:** تُحدد  
**Tests:** تُحدد  
**Documentation:** Required  
**Approval:** Pending

## 6.2 شروط الاحتفاظ بالمكون

يمكن الاحتفاظ بالمكون إذا:

- يندرج ضمن قاعدة MedClub المملوكة أو الاعتماديات الخارجية المعتمدة.
- يحقق المتطلبات الجديدة.
- لا يحتوي على ثغرات معروفة مانعة.
- يعمل بصورة موثوقة.
- لا يسبب ارتباطًا غير مطلوب بالنظام السابق.
- لا يفرض تكلفة صيانة غير مبررة.
- يمكن توثيقه واختباره.

## 6.3 شروط إعادة الكتابة

لا تتم إعادة الكتابة إلا عند وجود سبب مثل:

- خلل معماري يؤثر على الاستقرار.
- مشكلة أمنية تتطلب تغييرًا جذريًا.
- عدم إمكانية تعديل المكون بصورة معقولة.
- اعتماديات غير قابلة للصيانة.
- اختلاف جوهري بين منطق النظام القديم والجديد.
- تكلفة إصلاح أعلى بصورة مبررة من إعادة التنفيذ.

## 24.4 الأداء والاعتمادية

الأهداف الأولية المقترحة:

- LCP لا يتجاوز 2.5 ثانية للصفحات الحرجة في ظروف اختبار معتمدة.
- p95 لاستجابة API الأساسية أقل من 800ms ضمن حمل محدد.
- توافر شهري مستهدف 99.5%.
- نسخ احتياطي آلي.
- اختبار استعادة دوري.
- عدم تعطيل الـ Core API عند فشل THINK.
- عزل مهام تشغيل الكود عن الخدمات الأخرى.

تُعتمد الأهداف النهائية بعد اختبار الحمل وتحديد سعة النشر.

|---|---|
| Requirement ID | المعرف |
